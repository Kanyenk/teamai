# Règles permanentes TeamAI

## Environnement

- Dépôt canonique Ubuntu : `/home/ubuntu/projects/teamai`
- Branche de travail : `main`
- Environnement Hermes : `/opt/data/home/projects/teamai`
- Dossier d’échange permanent : `/opt/projects/teamai-exchange/`

## Livraison obligatoire

- Toutes les livrables TeamAI doivent être écrites dans :
  `/opt/projects/teamai-exchange/`
- Ne jamais utiliser `/opt/data/home/projects/teamai-export/` pour une livraison finale.
- Ne jamais générer de carte média, de lien de téléchargement ou de bloc texte contenant un patch.
- Toujours livrer des fichiers réels : patchs Git bruts, archive source ou documents Markdown.

## Format de livraison

Pour chaque lot, créer un dossier :

`/opt/projects/teamai-exchange/<nom-du-lot>/`

contenant :

- les patchs générés par `git format-patch`, dans l’ordre ;
- `source.tar.gz`, sans dossier `.git` ;
- `MANIFEST.md` avec contenu, commandes d’application et vérifications ;
- éventuellement une archive `.tar.gz` du dossier.

## Réponse de livraison

À la fin d’une livraison, répondre uniquement avec :

1. Chemin exact des fichiers livrés.
2. Taille de chaque fichier.
3. SHA256 de chaque fichier.
4. Commit de base attendu.
5. Commandes exactes d’application.
6. Résultat attendu après application.

## Règles de qualité

- Ne jamais inventer de chiffre, de mesure ou de résultat de test.
- Toute affirmation chiffrée doit citer une source ou être marquée « hypothèse — à tester ».
- Ne jamais écrire directement dans le dépôt canonique Ubuntu.
- Livrer uniquement des patchs Git purs, sans texte avant ou après.
- Respecter `docs/contrat-agents.md`.

# Règles permanentes TeamAI

## Livraison

- Toutes les livrables sont écrites dans `/opt/projects/teamai-exchange/`.
- Côté Ubuntu, ce dossier est `/home/ubuntu/projects/teamai-exchange/`.
- Aucune carte média, aucun lien de téléchargement, aucun patch dans un bloc texte.
- Les patchs sont des fichiers bruts `git format-patch`.
- Inclure `source.tar.gz` sans `.git` et un `MANIFEST.md`.
- Rapporter : chemin, taille, SHA256, commit de base attendu et commandes d’application.
- Respecter `docs/contrat-agents.md`.

## Règle des lots

- Un lot se fait toujours dans une copie du dépôt projet concerné.
- Ne jamais créer un dépôt Git isolé pour un lot.
- La branche du lot est créée depuis le commit de base indiqué par le fondateur.
- Les patchs sont générés avec git format-patch <commit-de-base>..<branche-du-lot>.
- Le dépôt original n’est jamais modifié directement.
- Si le commit de base est absent, arrêter et demander instruction.

## Interprétation des lots

- Un fichier absent mentionné dans un lot est un fichier à créer.
- Ne jamais considérer l’absence d’un fichier attendu comme une erreur ou une divergence.
- Ne pas comparer plusieurs fois le dépôt canonique et la copie.
- Exécuter une séquence numérotée une seule fois, dans l’ordre.
- Après génération des patchs et du MANIFEST, s’arrêter et livrer.
- En cas d’ambiguïté, poser une seule question au fondateur et attendre.

## Correction d’échec de script

- Si un script échoue, afficher uniquement les 40 dernières lignes de sortie.
- Identifier l’erreur exacte.
- Appliquer le correctif minimal.
- Relancer uniquement le script ou l’étape échouée.
- Ne jamais recommencer une analyse complète.
- Ne jamais comparer plusieurs fois le dépôt canonique et la copie.

## Correction d’API

- Avant de corriger un appel à une classe existante, inspecter une seule fois ses méthodes publiques avec inspect.getmembers.
- Ne jamais deviner le nom d’une méthode.
- Après inspection, appliquer le correctif minimal.
- Relancer uniquement les tests.
- Si l’échec persiste, afficher les 40 dernières lignes et attendre une instruction.

## Inspection avant correction

- Avant de corriger un appel à une classe existante, inspecter une seule fois ses méthodes publiques et signatures.
- Ne jamais deviner un nom de méthode ou une signature.
- Appliquer ensuite le correctif minimal.
- Relancer uniquement les tests.
- Si l’échec persiste, afficher les 40 dernières lignes et attendre une instruction.

## Contrat des classes existantes

- Avant d’intégrer une classe existante, inspecter une seule fois les méthodes et attributs nécessaires.
- Ne jamais deviner un identifiant, une signature ou un comportement.
- Utiliser inspect.getsource uniquement pour la méthode concernée.
- Appliquer ensuite le correctif minimal.
- Relancer uniquement les tests.
- Si l’échec persiste, afficher les 40 dernières lignes et attendre une instruction.

## Découverte des contrats

- Avant d’utiliser une classe existante, inspecter une seule fois ses constantes, signatures et méthodes nécessaires.
- Ne jamais deviner une valeur métier, un identifiant ou un état.
- Utiliser inspect.getsource uniquement pour la méthode ou classe concernée.
- Appliquer ensuite le correctif minimal.
- Relancer uniquement les tests.
- Si l’échec persiste, afficher les 40 dernières lignes et attendre une instruction.

## Intégration des classes existantes

- Avant d’écrire une API, inspecter une seule fois les constantes, signatures et méthodes nécessaires.
- Utiliser uniquement les contrats confirmés.
- Ne jamais deviner un type métier, un état, un identifiant ou une signature.
- Appliquer le correctif minimal.
- Relancer uniquement les tests.
- Si l’échec persiste, afficher les 40 dernières lignes et attendre une instruction.

## Initialisation des états

- Ne jamais appeler une méthode de transition pour initialiser un état.
- Définir directement l’état initial interne.
- Vérifier que l’état initial figure déjà dans l’historique `etats`.
- Appliquer le correctif minimal.
- Relancer uniquement les tests.
- Si l’échec persiste, afficher les 40 dernières lignes et attendre une instruction.

## Application des patches

- Ne jamais supposer que `.hermes.md` est identique entre Hermes et Ubuntu.
- Avant `git am`, tester `git apply --check`.
- En cas de conflit uniquement sur `.hermes.md`, appliquer le patch avec `--exclude='.hermes.md'`.
- Créer ensuite un commit dédié au code fonctionnel.
- Relancer les tests après application.

## Application incrémentale

- Après `git apply`, inspecter `git status` avant de committer.
- Ne committer que les fichiers réellement modifiés.
- Si certains fichiers du patch existent déjà à l’identique, ne pas les réajouter.
- Créer un commit dédié au diff restant.
- Relancer les tests après commit.

## Exceptions homonymes

- Ne jamais importer une exception par son nom seul lorsqu’il existe plusieurs modules.
- Vérifier la classe réellement attendue par le test ou l’appelant.
- Importer depuis le module qui définit le contrat utilisé, par exemple `engine.exceptions`.
- Appliquer le correctif minimal.
- Relancer les tests.

## Corrections d’imports

- Ne jamais remplacer une ligne d’import sans vérifier son texte exact.
- Utiliser une recherche par symbole, pas une correspondance littérale fragile.
- Après modification, relancer les tests.
- Si l’échec persiste, inspecter la définition réelle avant de modifier le moteur.

## Imports multi-symboles

- Ne jamais remplacer une ligne d’import multi-symboles par un import d’un seul symbole.
- Avant modification, lister tous les symboles utilisés dans le fichier.
- Séparer les imports : moteur d’un côté, exceptions de l’autre.
- Après modification, relancer toute la suite de tests.
- Ne jamais réexécuter un script de remplacement ayant déjà causé des NameError.

## Tests de validation

- Un test qui vérifie une erreur doit utiliser assertRaises.
- Vérifier la classe exacte levée par la fonction testée.
- Ne jamais supposer que deux exceptions homonymes sont interchangeables.
- Afficher le bloc de test concerné avant toute modification.

## Exceptions homonymes et alias

- Lorsque deux exceptions portent le même nom, importer celle du moteur avec un alias.
- Utiliser l’alias dans les tests qui vérifient les erreurs levées par le moteur.
- Conserver l’import du module d’exceptions pour ses propres contrats.
- Relancer toute la suite après modification.

## Authentification Git

- Utiliser les variables GitHub déjà présentes dans les environnements Hermes ou Docker.
- Ne jamais écrire un token dans l’URL d’un remote.
- Ne jamais afficher la valeur d’un token dans un terminal ou un log.
- Préférer un credential helper à un token intégré dans l’URL.
- Vérifier `git remote -v` avant tout push.

## Remote GitHub

- Ne jamais laisser un placeholder tel que TON_UTILISATEUR dans une URL de remote.
- Vérifier git remote -v après toute création ou modification de remote.
- Utiliser l’URL réelle du dépôt GitHub.
- Après git fetch, comparer les branches locales et distantes avant tout push.
- Ne jamais force-pusher sans instruction explicite.

## Synchronisation main

- Avant tout push vers main, exécuter :
  git fetch origin
  git rev-list --left-right --count main...origin/main
- Si les historiques divergent, ne ni merger ni force-pusher automatiquement.
- Afficher les deux historiques et attendre une décision.
- Préférer un merge explicite ou un rebase local décidé par l’utilisateur.
- Relancer les tests après toute synchronisation.

## Historiques divergents

- Si git rev-list indique des commits des deux côtés, ne jamais force-pusher.
- Créer d’abord des branches de sauvegarde locale et distante.
- Lancer git merge --no-commit --no-ff.
- Lister les conflits et attendre une décision avant résolution.
- Après résolution, relancer toute la suite de tests.
- Pousser uniquement après tests verts et validation utilisateur.

## Historiques sans ancêtre commun

- Si git merge refuse avec “unrelated histories”, ne jamais forcer un push.
- Créer des branches de sauvegarde avant toute action.
- Utiliser git merge --allow-unrelated-histories --no-commit --no-ff.
- Lister les conflits et attendre une décision avant résolution.
- Après résolution, relancer toute la suite de tests.
- Pousser uniquement après tests verts et validation utilisateur.

## Résolution de conflits

- Pour un merge de branches sans ancêtre commun, créer des sauvegardes avant résolution.
- Si une version locale est validée par les tests, utiliser `--ours` pour les fichiers en conflit.
- Retirer les artefacts générés et les fichiers distants non utilisés par la version validée.
- Relancer toute la suite de tests avant de committer le merge.
- Ne jamais pousser avant validation utilisateur.

## Publication de main

- Après un merge validé, pousser immédiatement main.
- Vérifier ensuite git fetch et git status.
- Confirmer que origin/main pointe sur le commit local.
- Ne jamais considérer un merge comme publié avant un push réussi.

## Automatisation des push

- Hermes est responsable des push Git pour TeamAI.
- Le dépôt de référence est /opt/projects/teamai dans le conteneur.
- Ne jamais pousser depuis un autre clone ou workspace.
- Avant chaque push : vérifier remote, branche, propreté et HEAD.
- Utiliser le token de l’environnement, sans l’afficher ni l’écrire dans l’URL.
- Ne jamais force-pusher.
- Après push : git fetch, git status, et confirmation du commit publié.

## Permissions Git

- Le dépôt hôte appartient à l’utilisateur Ubuntu ; Hermes tourne sous UID 10000.
- Après création ou modification du dépôt, appliquer :
  sudo setfacl -R -m u:10000:rwx .git
  sudo setfacl -R -d -m u:10000:rwx .git
- Hermes peut alors mettre à jour les refs distantes après push.
- Ne jamais utiliser chown -R sur tout le dépôt.
- Après correction, vérifier git fetch origin et git status.

## Lots de développement

- Chaque lot démarre depuis main à jour.
- Chaque lot utilise une branche dédiée.
- Chaque lot ajoute ses propres tests.
- Aucun lot ne modifie les tests existants pour masquer une régression.
- Un lot n’est terminé que lorsque tous les tests passent et que la branche est poussée.
- Après push, Hermes confirme branche, tests et commit publié.

## Dépôt de référence et permissions

- Le dépôt de référence est /opt/projects/teamai dans le conteneur.
- Hermes ne doit jamais travailler dans /opt/data/home/projects/teamai pour les lots TeamAI.
- Le dépôt hôte doit accorder rwx à UID 10000 sur l’arbre et .git via ACL.
- Avant chaque lot : vérifier pwd, git remote -v, git branch et git status.
- Toute branche créée depuis un mauvais clone doit être supprimée et refaite depuis main.
- Ne jamais considérer un lot comme terminé s’il n’a pas été réalisé dans le dépôt de référence.

## Intégration des lots

- Un lot est terminé lorsque sa branche est poussée et tous les tests passent.
- L’intégration dans main se fait par git merge --no-ff.
- Après merge, relancer toute la suite de tests.
- Pousser main uniquement après tests verts.
- Ne jamais supprimer une branche de lot sans instruction explicite.
- Après push, vérifier git fetch et git status.

## Hygiène du dépôt

- Ignorer les fichiers d’édition : *.swp, *.swo, .hermes.md.swp.
- Ne jamais committer un fichier de swap.
- Vérifier git status avant chaque commit.
- Un arbre propre est obligatoire avant push.

## Intégration des lots HTTP

- Après un lot http-api vert, intégrer par git merge --no-ff dans main.
- Relancer toute la suite de tests après merge.
- Pousser main uniquement après tests verts.
- Ne jamais supprimer la branche du lot sans instruction.
- Le lot suivant est http-api-hardening : validation et codes HTTP.

## Qualité et CI

- Chaque push sur main déclenche les tests via GitHub Actions.
- Aucun warning de dépréciation ne doit rester dans les tests.
- Les logs HTTP ne doivent pas polluer la sortie des tests.
- Un lot CI doit être validé par les tests locaux avant push.
- Après merge, vérifier l’exécution du workflow sur GitHub.

## Intégration CI

- Toute branche de lot doit passer tous les tests avant merge.
- Le merge dans main déclenche le workflow GitHub Actions.
- Après merge, vérifier l’exécution du workflow sur GitHub.
- Aucun DeprecationWarning ne doit être toléré.
- Utiliser python -W error::DeprecationWarning pour valider l’absence de warning.

## Validation métier

- Toute création de document doit passer par DocumentValidator.
- Toute transition doit vérifier l’état courant et la table TRANSITIONS.
- Aucune règle métier ne doit être dupliquée entre API, moteur et tests.
- Chaque règle doit avoir au moins un test positif et un test négatif.
- Relancer les tests avec -W error::DeprecationWarning avant tout push.

## Intégration des lots de validation

- Toute règle métier doit être centralisée dans DocumentValidator.
- L’API ne doit jamais dupliquer une règle déjà présente dans le validateur.
- Chaque règle doit avoir au moins un test positif et un test négatif.
- Après merge, relancer les tests avec -W error::DeprecationWarning.
- Vérifier le workflow GitHub Actions après push de main.

- Les tests utilisent des tokens fictifs.
- Relancer les tests avec -W error::DeprecationWarning avant tout push.
- Vérifier le workflow GitHub Actions après merge dans main.

## Intégration de l’authentification

- La sécurité BearerAuth doit être documentée pour toutes les routes protégées.
- Toute nouvelle route doit être ajoutée à la documentation dans le même lot.
- Relancer les tests avec -W error::DeprecationWarning avant tout push.

## Intégration de la documentation

- Toute nouvelle route HTTP doit être ajoutée à docs/openapi.yaml dans le même lot.
