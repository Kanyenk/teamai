## 0. Projets et gouvernance

### Projets actifs

  - Charter : `xohive/CHARTER.md`
  - Vision produit : `xohive/PRODUCT_VISION.md`
  - Handover : `xohive/HANDOVER.md`
  - Backlog : `xohive/BACKLOG.md` (à créer)
  - Architecture : `xohive/docs/architecture/` (à créer)

### Règle multi-projets

- Chaque projet a son propre dossier `<nom>/` à la racine du dépôt.
- Dans chaque dossier projet : `CHARTER.md`, `PRODUCT_VISION.md`, `HANDOVER.md`, `BACKLOG.md`.
- Les docs d’architecture vont dans `<projet>/docs/architecture/`.
- Aucun fichier de projet à la racine du dépôt.
- Avant toute tâche, identifier le projet concerné et lire son dossier dédié.
- Avant `git mv`, vérifier que le fichier est versionné (`git ls-files`).

### Convention de nommage

- Un projet = un dossier à la racine.
- `.hermes.md` = règles globales + liste des projets uniquement.
- Le code métier reste dans `engine/`, `tests/`, etc.

## Pilotage XoHive

- Toute nouvelle tâche vient de xohive/BACKLOG.md.
- Chaque tâche suit le cycle : branche → implémentation → tests → doc → PR.
- Les 90 tests doivent toujours passer.
- Le domain model (xohive/docs/architecture/domain-model.md) fait foi pour les entités.
- Un sprint = 3 tâches maximum.

## Gestion du code xohive

- Tout code métier XoHive va dans xohive/domain/ (modèles) et xohive/services/ (logique).
- Avant commit, vérifier cohérence avec xohive/docs/architecture/domain-model.md.
- Toute nouvelle entité doit avoir ses tests unitaires.
- Ne jamais committer du code incomplet ou non testé.

## Qualité du code xohive

- Toute entité du domain model doit avoir son fichier de test dans tests/.
- Avant commit d’une entité, vérifier :
  1. Le modèle correspond à domain-model.md
  2. Le repository couvre create/get/list/update/delete
  3. Les tests unitaires existent et passent
- Ne jamais committer une entité sans ses tests.
- Après commit, vérifier git status = clean.

## Permissions et qualité

- Hermes (uid 10000) ne doit jamais écrire directement dans .git du dépôt canonique (uid 1001).
- Après toute création de fichier par Hermes, corriger les permissions :
  sudo chown -R ubuntu:ubuntu <fichiers>
- Avant tout commit, les tests doivent passer à 100%.
- En cas d’échec de test, corriger le code ou le test avant de committer.
- Ne jamais committer avec des tests en échec.

## Workflow de contribution

- Toute nouvelle fonctionnalité se fait sur une branche feature/<nom>.
- Avant PR, les tests doivent passer à 100%.
- La PR doit lister : modèle, repository, tests.
- Le merge dans main se fait avec --no-ff pour garder l’historique.
- Après merge, vérifier git status = clean et tests OK sur main.
