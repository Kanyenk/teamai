# Règles permanentes TeamAI

## Environnement

- Dépôt canonique Ubuntu : `/home/ubuntu/projects/teamai`
- Branche de travail : `main`
- Environnement Hermes : `/opt/data/home/projects/teamai`
- Dossier d’échange permanent : `/opt/projects/teamai-exchange/`
- Chemin équivalent côté Ubuntu : `/home/ubuntu/projects/teamai-exchange/`

## Livraison obligatoire

- Toutes les livrables TeamAI doivent être écrites dans :
  `/opt/projects/teamai-exchange/`
- Ne jamais utiliser `/opt/data/home/projects/teamai-export/` pour une livraison finale.
- Ne jamais générer de carte média, de lien de téléchargement ou de bloc texte contenant un patch.
- Toujours livrer des fichiers réels : patchs Git bruts, archive source ou documents Markdown.

## Format de livraison

Pour chaque lot, créer un dossier :

`/opt/projects/teamai-exchange/<nom-du-lot>/`

contenant :

- les patchs générés par `git format-patch`, dans l’ordre ;
- `source.tar.gz`, sans dossier `.git` ;
- `MANIFEST.md` avec contenu, commandes d’application et vérifications ;
- éventuellement une archive `.tar.gz` du dossier.

## Réponse de livraison

À la fin d’une livraison, répondre uniquement avec :

1. Chemin exact des fichiers livrés.
2. Taille de chaque fichier.
3. SHA256 de chaque fichier.
4. Commit de base attendu.
5. Commandes exactes d’application.
6. Résultat attendu après application.

## Règles de qualité

- Ne jamais inventer de chiffre, de mesure ou de résultat de test.
- Toute affirmation chiffrée doit citer une source ou être marquée « hypothèse — à tester ».
- Ne jamais écrire directement dans le dépôt canonique Ubuntu.
- Livrer uniquement des patchs Git purs, sans texte avant ou après.
- Respecter `docs/contrat-agents.md`.

# Règles permanentes TeamAI

## Livraison

- Toutes les livrables sont écrites dans `/opt/projects/teamai-exchange/`.
- Côté Ubuntu, ce dossier est `/home/ubuntu/projects/teamai-exchange/`.
- Aucune carte média, aucun lien de téléchargement, aucun patch dans un bloc texte.
- Les patchs sont des fichiers bruts `git format-patch`.
- Inclure `source.tar.gz` sans `.git` et un `MANIFEST.md`.
- Rapporter : chemin, taille, SHA256, commit de base attendu et commandes d’application.
- Respecter `docs/contrat-agents.md`.

## Règle des lots

- Un lot se fait toujours dans une copie du dépôt projet concerné.
- Ne jamais créer un dépôt Git isolé pour un lot.
- La branche du lot est créée depuis le commit de base indiqué par le fondateur.
- Les patchs sont générés avec git format-patch <commit-de-base>..<branche-du-lot>.
- Le dépôt original n’est jamais modifié directement.
- Si le commit de base est absent, arrêter et demander instruction.

## Interprétation des lots

- Un fichier absent mentionné dans un lot est un fichier à créer.
- Ne jamais considérer l’absence d’un fichier attendu comme une erreur ou une divergence.
- Ne pas comparer plusieurs fois le dépôt canonique et la copie.
- Exécuter une séquence numérotée une seule fois, dans l’ordre.
- Après génération des patchs et du MANIFEST, s’arrêter et livrer.
- En cas d’ambiguïté, poser une seule question au fondateur et attendre.

## Correction d’échec de script

- Si un script échoue, afficher uniquement les 40 dernières lignes de sortie.
- Identifier l’erreur exacte.
- Appliquer le correctif minimal.
- Relancer uniquement le script ou l’étape échouée.
- Ne jamais recommencer une analyse complète.
- Ne jamais comparer plusieurs fois le dépôt canonique et la copie.

## Correction d’API

- Avant de corriger un appel à une classe existante, inspecter une seule fois ses méthodes publiques avec inspect.getmembers.
- Ne jamais deviner le nom d’une méthode.
- Après inspection, appliquer le correctif minimal.
- Relancer uniquement les tests.
- Si l’échec persiste, afficher les 40 dernières lignes et attendre une instruction.
